01 / 这个仓库解决什么问题

玩家组队或匹配成功后，系统找到一个有容量的节点，创建一局游戏服务器，把连接地址返回给玩家，并在对局结束或发生故障时回收资源。

关注范围：匹配、对局分配和服务器生命周期管理。实际游戏中的移动、射击、伤害计算与状态同步，仍由 UE 游戏服务器承担。

GogRPCProtobufRedisMongoDB

仓库提供 Docker Compose 和 Kubernetes 部署示例，采用 MIT 许可证。

02 / 各模块的职责

模块角色主要职责
gameserverGS：玩家与匹配服务维护玩家 TCP 连接，处理登录、组队匹配，并把对局地址返回给玩家。
dscserverDSC：调度器接收创建对局请求、选择 Agent、维护分配状态，并清理异常实例。
dsaserverDSA：节点代理服务管理本节点端口、请求模板创建实例，并向 DSC 上报实例事件。
dstemplate模板与实例模拟器模拟模板就绪、创建对局实例、实例就绪和停止流程，供协议联调。
store存储访问层使用 Redis 保存控制状态、索引和通知，使用 MongoDB 保存用户与玩家数据。
proto / pb协议定义与生成代码proto 定义 TCP 消息与 gRPC 接口；pb 保存生成的 Go 代码。

当前实现边界：dstemplate 使用 goroutine 和 TCP 监听模拟实例，没有实现真正的 UE 进程 Fork。接入 UE 时，需要替换或扩展这一层。

03 / 一次创建对局的核心流程

玩家发起匹配
→
GS组队、创建 Realm
→
DSC选择 Agent
→
DSA分配端口、请求创建
→
模板 → DS创建并上报就绪

核心调用链路时序图

从上往下看时间顺序，箭头表示发送方 → 接收方。蓝色为创建，绿色为就绪通知，紫色为游戏连接，橙色为结束回收。窄屏可左右滑动查看。

  1. 玩家 → GS：玩家通过 TCP 登录并加入匹配队伍 Team。
  2. GS → DSC：队伍满足开局条件后，GS 在 Redis 写入 Realm 骨架，再通过 gRPC 调用 CreateRealm。
  3. DSC → DSA：调度器选择在线、模板就绪且有容量的 Agent，预占容量，并向其 DSA 调用 CreateDS。
  4. DSA → 模板：DSA 分配游戏端口，通过 TCP 管理连接发送 ForkInstance。
  5. DS → DSA → DSC：实例启动就绪后发送 DSCreateOK；DSA 将其转换为 ReportDSEvent(READY) 上报。
  6. DSC → Redis → GS：调度器更新对局状态并发布就绪通知；GS 向玩家发送 DS 地址。
  7. 玩家 → DS：玩家使用得到的游戏地址连接对局服务器。接入 UE 后，游戏流量使用 UE 的网络协议。
  8. 结束或故障：实例事件与超时巡检触发清理，回收实例、释放端口和容量，并清理玩家映射。

关键区别：CreateDS 返回成功，只表示本次创建请求已经受理。必须等实例上报 CreateOK 并形成 READY 事件，才能认为游戏服务器已就绪。

04 / 先弄清四个对象

对象含义学习时需要回答的问题
Team匹配中的队伍。谁加入了队伍？何时满员、强制开始或超时？
Realm一场逻辑对局，记录玩家与对局状态。有哪些玩家？正在创建、已就绪、游戏中，还是已结束或失败？
DS承载对局的服务器实例；当前模拟器中的实例不等同于独立 UE 进程。何时真正启动成功？监听哪个地址？何时退出和回收？
Agent向 DSC 注册的 DSA 节点代理。是否在线？模板是否就绪？容量是多少？管理了哪些 DS？

关系：Team 满足条件后形成 Realm；Realm 申请一个 DS 承载；DS 由某个 Agent 对应的 DSA 管理。

Realm 与 DS 的区别：Realm 描述“这一局是什么、有哪些玩家”，DS 描述“这一局由哪个运行实例承载”。逻辑对局已创建时，实际 DS 可能仍在启动。

05 / Agent 与 DSA 到底是什么关系

当前仓库中，一个 Agent 对应一个运行并注册到 DSC 的 DSA 服务实例。DSA 是实际服务程序；Agent 是调度器中对该服务实例的登记与描述。

名称具体含义
dsaserverDSA 服务的源码目录，也是构建入口所在位置。
DSA 实例实际运行的一个 DSA 服务进程，负责管理一批对局实例。
AgentDSC 中对该 DSA 的记录，包括身份、管理地址、容量、实例计数、心跳和模板就绪状态。
agentID该节点代理的唯一标识，例如 Agent-A；运行配置使用 DS_DSA_AgentID。
DS 实例承载某一局游戏的实例；同一个 DSA 可以管理多个 DS。

从程序启动到实例管理

启动 dsaserver 程序
    ↓
运行一个 DSA 服务进程
    ↓ 使用 agentID 向 DSC 注册
DSC 将其登记为一个 Agent
    ↓
该 DSA 管理多个 DS 对局实例

一个具体例子

DSC 调度器
├─ Agent-A（对应一个 DSA 服务实例）
│  ├─ DS-001：第一局
│  └─ DS-002：第二局
└─ Agent-B（对应另一个 DSA 服务实例）
   └─ DS-003：第三局

“DSC 选择一个 Agent”，实际意味着选择该 Agent 登记的 gRPC 管理地址，再调用对应 DSA 的 CreateDS 接口。

Agent 不等于物理机器。一台机器可以运行多个 DSA 实例，但需要使用不同的 agentID，并确保监听端口和实例游戏端口不冲突。同一机器上的资源仍然由这些实例共同使用。
