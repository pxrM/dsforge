## 源码事实

- [dstemplate/main.go](../dsserver/dstemplate/main.go) 的 `handleFork` 和 `instanceCtx.start` 目前仅模拟实例，监听 TCP 端口并上报 CreateOK。
- [dsmgr.go](../dsserver/dsaserver/dsa/dsmgr.go) 的 `NewDS` 分配端口并调用模板 `ForkInstance`，没有直接启动 UE 可执行程序。
- [dsa_ds.proto](../dsserver/proto/dsa_ds.proto) 定义了 TemplateReady、ForkInstance、CreateOK、ForkFailed、StopDS、DSUpdateState、DSGameEnd。
- ForkInstance 携带 DSID、RealmID、RealmCfgID、端口及 AdvertiseIP。
- [ds_msg.go](../dsserver/dsaserver/dsa/ds_msg.go) 将实例消息转换成 DSC 事件；[report.go](../dsserver/dscserver/dsareport/report.go) 推进 Realm/DS 状态并回收。
- [client_server.proto](../dsserver/proto/client_server.proto) 的 JoinRealmOKResp 携带配置、DS 地址和 TeamID。

## 自己的理解：先做最小接入

首版建议“一局一个 UE Server 进程”。先验证进程启动、就绪、玩家连接和回收，再研究真正的模板 Fork。
以下是计划，不是现有功能：用一个启动器适配模板协议，收到创建请求后启动 UE Dedicated Server，并管理 PID、退出状态和超时。

必须先确定“谁负责实例侧协议”：UE Server 本身，或一个代为通信的适配器。若由适配器负责，必须建立可靠的就绪与结束信号，不能把进程成功启动直接当作游戏可连接。

### 分阶段验收

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| A. 单独验证 UE DS | 构建服务器，手工启动并连接 | 两个客户端进入同一服务器，基本复制和对局流程正常 |
| B. 修复并跑通模拟系统 | 处理问题清单中的匹配和地址阻断项 | 模拟对局创建、通知、连接、回收闭环稳定 |
| C. 进程启动适配 | 接收 ForkInstance，分配参数，启动一个 UE Server | 日志可关联 DSID/RealmID/PID/端口；启动失败返回 ForkFailed |
| D. 实例协议适配 | 实现连接、就绪、状态、结束与停止 | 实际就绪后才通知玩家；结束或取消后实例退出且端口回收 |
| E. 客户端接入 | 接收分配地址并发起 UE ClientTravel | 匹配完成后自动进入正确实例，失败有明确反馈 |
| F. 多局与异常验证 | 多端口并行、启动失败、取消、崩溃 | 无串局、无孤儿进程、容量与端口最终一致 |

### 协议责任草案

| 消息 | 接入方需要实现的行为 |
| --- | --- |
| TemplateReady | 启动器可接收创建请求时上报；与某局游戏 ready 区分 |
| ForkInstance | 解析标识、配置、端口与地址，启动对应进程 |
| ForkFailed | 启动或初始化失败时返回 DSID 和原因 |
| CreateOK | 游戏已完成必要初始化并可接受连接后，上报 DSID/RealmID/实际地址 |
| DSUpdateState | 按确认后的协议语义更新实例活动状态；当前后端将其映射为 PLAYER_ENTER |
| DSGameEnd | 一局结束时通知；需要与意外进程退出区分 |
| StopDS | 请求目标实例停止；设计超时后的进程终止兜底 |

注意：当前 backend 的 dsUpdateState 忽略消息体并报告 PLAYER_ENTER。不能直接把“任意心跳”都当作玩家进入，需要先确定并调整语义。

### 网络与生命周期检查

- 控制通信与 UE 游戏通信分别确认；仓库模拟器的 TCP 可连接，不能证明 UE 游戏流量可达。
- 按实际 UE 网络驱动确认 TCP/UDP 需求，检查 Compose、hostPort、防火墙和安全组。
- 返回地址必须从客户端机器可达，不能直接采用只在容器内部有效的服务名。
- 不在 Go 程序退出前提前释放仍由 UE 进程占用的端口。
- 取消、迟到 CreateOK、停止失败和启动器崩溃都需要验证进程确实被回收。
